\subsection{Implementación gRPC}
El contrato se convierte a Python mediante el script
\texttt{scripts/generate\_proto.py}. El servidor utiliza los mensajes generados
y completa la función remota \texttt{EnviarMensaje}.

Antes de procesar una solicitud se comprueba que el identificador no esté vacío,
el emisor corresponda a uno de los tres nodos y el timestamp no sea negativo.
También se comprueba que el reloj tenga espacio para avanzar dentro de
\texttt{int64}. Los campos inválidos producen una respuesta de error de gRPC.

\texttt{GRPCServer} reutiliza la configuración,
\texttt{LamportClock} y \texttt{EventLogger} de la base común. Registra la recepción
con \texttt{receive\_event} y el envío del acuse con \texttt{send\_event}; el texto
de confirmación es \texttt{ACK}, como en TCP.
El servidor comprueba el identificador, el nombre del nodo que responde y el reloj
del acuse antes de devolverlo. La atención utiliza un grupo de hilos y el reloj
compartido protege la actualización y el registro de cada evento.
El servidor no crea otro reloj permanente ni escribe directamente los CSV.

El script \texttt{scripts/validate\_grpc\_server.py} permite comprobar esa
integración con tres procesos y un único escritor CSV. En la ejecución manual
del 19 de noviembre se completaron tres intercambios: uno de A hacia B y dos
envíos concurrentes de A y C hacia B. El CSV contiene doce eventos y seis parejas
de envío y recepción con reloj de recepción mayor que el de envío.

La solicitud con identificador vacío produjo \texttt{INVALID\_ARGUMENT}; el reloj
de B permaneció en 9. Los tres procesos terminaron correctamente. Se conservaron
los registros originales y cuatro capturas. Esta validación del servidor no
incluye mediciones de latencia ni sustituye el protocolo comparativo final.
Las corridas completas siguen pendientes.

\subsubsection{Cliente gRPC}
\texttt{GRPCClient} mantiene un canal por destinatario. El método
\texttt{prepare} espera que el canal esté disponible antes del tramo medido.
La interfaz \texttt{exchange} permite al coordinador usar el mismo esquema de
argumentos y resultados que el cliente TCP.

Antes de enviar se comprueban los argumentos, se incrementa el reloj y se registra
el evento. Al recibir se valida el identificador, el emisor, el texto \texttt{ACK}
y el timestamp; después se actualiza y registra el reloj de recepción.
El RTT se obtiene con \texttt{time.perf\_counter()} e incluye el envío y la
validación y registro del acuse. Los canales se reutilizan y no se programa una
política de reintentos. Los fallos se conservan como \texttt{timeout} o
\texttt{error}, con RTT vacío.

Se preparó \texttt{scripts/demo\_grpc.py} para ejecutar el plan común de veinte
intercambios con cargas de 100 y 10240 bytes y con tres emisores concurrentes.
Nixon ejecutó las seis pruebas del cliente el 20 de noviembre y todas terminaron
correctamente. Después se realizaron tres validaciones funcionales: secuencial
con 100 bytes, secuencial con 10240 bytes y concurrente con tres emisores y
100 bytes. Cada ejecución completó 20 de 20 intercambios sin fallos.

Cada corrida produjo 80 eventos, 20 registros de RTT y una fila de lote. Se
comprobaron 40 parejas de envío y recepción por corrida, con reloj de recepción
mayor al de envío. Se conservaron los CSV y capturas originales. Estas ejecuciones
comprueban el cliente; no sustituyen el calentamiento y las cinco repeticiones
del experimento comparativo.
